# AI agent guidelines for narakcode.dev

Next.js 16 (App Router) portfolio, blog, and shadcn registry website.

**Stack**: TypeScript, React 19, Tailwind CSS v4, shadcn/ui, MDX, Vitest, pnpm (Bun for scripts), Vercel

## Project structure

| Directory                              | Purpose                                                                                     |
| -------------------------------------- | ------------------------------------------------------------------------------------------- |
| `src/app/`                             | App Router pages, layouts, API routes                                                       |
| `src/components/`                      | Shared UI components                                                                        |
| `src/registry/`                        | Registry source (components, hooks, blocks, examples, lib)                                  |
| `src/features/`                        | Feature modules: `doc`, `blog`, `portfolio`, `sponsor`, `blocks`, `icons`, `tools`, `vault` |
| `src/config/`                          | Site (`site.ts`), registry (`registry.ts`), JSON-LD config                                  |
| `src/scripts/`                         | Build scripts (registry, capture) run with Bun                                              |
| `src/hooks/`, `src/lib/`, `src/utils/` | Hooks, libraries, utilities                                                                 |

**Key files**: `components.json` (shadcn config), `src/features/portfolio/data/` (portfolio data), `.env.example` (env vars)

## Component registry

Built on shadcn/ui. Registry types and their definition files:

| Type                 | File                                   |
| -------------------- | -------------------------------------- |
| `registry:component` | `src/registry/components/_registry.ts` |
| `registry:hook`      | `src/registry/hooks/_registry.ts`      |
| `registry:block`     | `src/registry/blocks/_registry.ts`     |
| `registry:example`   | `src/registry/examples/_registry.ts`   |
| `registry:lib`       | `src/registry/lib/_registry.ts`        |
| `registry:style`     | `src/registry/styles/_registry.ts`     |

**NEVER EDIT** auto-generated outputs of `pnpm registry:build`: `registry.json`, `registry-stats.json`, `src/registry/__index__.tsx`, `public/r/*.json`

### Adding a new component

1. Create component in `src/registry/components/[name]/`
2. Register in the appropriate `_registry.ts` file
3. Create example in `src/registry/examples/`
4. Run `pnpm registry:build`
5. Add docs MDX in `src/features/doc/content/components/` (category is derived from the folder)

## Content system

All content lives in `src/features/doc/content/` as MDX files, split into `blog/` and `components/`. The category is derived from the immediate subfolder name (not declared in frontmatter), so a file's location determines whether it's a blog post or component doc.

- **Data layer**: `src/features/doc/data/documents.ts` (`getAllDocs`, `getDocBySlug`, `getDocsByCategory`)
- **Blog UI**: `src/features/blog/` (rendering only, imports data from `features/doc`)

## Coding guidelines

- TypeScript strict mode; explicit types when necessary
- kebab-case file naming
- Descriptive names; comments only for "why", not "what"
- No emojis in code, comments, or commit messages
- Tailwind CSS v4 syntax; support dark/light modes
- Follow SOLID principles
- Headings in sentence-case (capitalize only the first word and proper nouns), applies to Markdown/MDX docs and prose

## UI design cleanup

### Context

The app is already built and running, and parts of its UI were drafted or
generated by an AI model. Models produce averages, not taste — left alone they
converge on the same look: purple gradients, all-caps eyebrow labels, icons in
glowing circles, glowing buttons, and everything animating in on a staggered
fade.

Vague direction ("modern", "clean", "sleek") does not fix this — the model
fills those words with its defaults. What fixes it is explicit, written-down
decisions. The rules in **Guardrails** are binding for the entire pass.

### Goal

Remove the AI look from the UI in one pass: inventory every tell, codify the
findings as a binding `DESIGN_RULES.md`, bring the whole UI into compliance,
and verify the result with screenshots instead of reading code blind.

### Inputs

- `{{UI_SCOPE}}` — the screens, routes, or components to cover. If none are
  specified, cover every user-facing screen.
- `{{DESIGN_REFERENCE}}` — optional: a component library, existing screens, or
  screenshots of apps whose design you like, to use as the starting point for
  rebuilt components. Starting from a good reference keeps components good;
  starting from zero produces the average. If none is given, work from the
  best existing components in the repo.

### Instructions

Work through the phases in order across `{{UI_SCOPE}}`.

#### Phase 1 — Inventory the AI tells

Scan `{{UI_SCOPE}}` for the known tells. Check both the rendered UI
(screenshots) and the code:

- Literal hex color codes outside token definitions — a raw hex in component
  code is already a tell.
- Gradients, glows, drop shadows on non-floating elements, nested cards.
- All-caps text and eyebrow labels; Title Case headings.
- Font weights outside regular and medium; font sizes off the type scale.
- Icons inside rounded boxes or circles; emojis in UI copy.
- Numbered list styling (01, 02, 03); status indicators that are a green check
  in a circle; avatars that fan out on hover; colored bars marking selected
  rows; fake logos that are a letter in a rounded square.
- Animations over 300ms, bounce easing, staggered entrances.
- Vague marketing copy in UI text ("Seamlessly", "Unlock", "Supercharge").

Also note any existing design tokens, type scale, and component primitives the
project already has — fixes should build on them, not replace them.

#### Phase 2 — Write DESIGN_RULES.md

Create `DESIGN_RULES.md` at the repository root, written so any agent can
follow it before touching UI. Organize it as a **Never** list and an **Always**
list:

- **Never** — every banned pattern found in Phase 1, one line each, with the
  reason next to it where the reason isn't obvious.
- **Always** — the semantic token set (background, surface, foreground,
  text-secondary, border, accent — adjust names to the project's existing
  tokens), the type scale with its weights, the corner radii, and the motion
  budget as numbers in milliseconds, not adjectives.
- Every line is a decision, not a preference — "no gradients" works, "make it
  elegant" doesn't.
- If the project already has an equivalent rules file, update it rather than
  creating a second one.

#### Phase 3 — Fix every violation

- Replace raw hex codes with the semantic tokens. Surfaces stay neutral; the
  accent appears only when something is actually active or selected.
- Collapse typography onto one scale with regular and medium weights only.
- Remove gradients, glows, and nested cards. Shadows only on elements that
  float (dropdowns, modals, popovers, toasts).
- Rebuild the banned component patterns (icons in rounded boxes,
  check-in-circle statuses, numbered list items, fanning avatars, colored
  selection bars, letter-in-a-square logos) — start from
  `{{DESIGN_REFERENCE}}` when provided.
- Bring all interface motion under the budget: under 300ms, exits faster than
  entries, no bounce, buttons press down to ~0.97 scale, keyboard-driven
  highlights move instantly — only the mouse gets the glide.
- Rewrite vague copy to be short and specific.

#### Phase 4 — Verify with screenshots

- Screenshot every screen in scope with a headless browser: light mode, dark
  mode if the app supports it, and phone width (~375px).
- Check each screenshot against `DESIGN_RULES.md` — clipped text, broken dark
  mode, and any gradient or glow that snuck back in count as failures.
- Fix failures and re-screenshot until the set is clean.

#### Phase 5 — Cut

Do a final deletion pass over each screen:

- Subtitles that restate the heading.
- Badges, icons, and decorations nobody asked for.
- Second shadows and redundant borders.
- An icon next to every label.

Remove rather than restyle — a calm screen with one good interaction beats
five effects fighting each other.

### Output format

- `DESIGN_RULES.md` at the repository root — the binding rules file.
- The fixes, applied to the repository through its normal change flow.
- Before/after screenshots for each fixed screen, saved under
  `unslop-ui-design/` or the repo's existing screenshot location.
- A report written to `unslop-ui-design-report.md` at the repository root:
  - tells found and how they were fixed, grouped by phase;
  - anything found but not fixed, with the reason;
  - the final screenshot set from Phase 4.

### Guardrails

These rules are binding — apply them to your own output as well as the code
you change:

- Sentence case everywhere. No all caps, no eyebrow labels.
- Regular and medium font weights only; one type scale.
- No raw hex codes outside token definitions — semantic tokens only.
- Surfaces stay neutral; the accent only appears on active or selected states.
- No gradients, no glow, no nested cards. Shadows only on elements that float.
- No icons inside rounded boxes or circles; no emojis in UI copy.
- No numbered list styling, no green-check-in-a-circle statuses, no avatars
  fanning out on hover, no colored bars on selected rows, no
  letter-in-a-rounded-square logos.
- Interface motion under 300ms; exits faster than entries; no bounce; buttons
  press to ~0.97; keyboard highlights move instantly.
- Don't start components from zero when a good reference exists.
- Don't change product behavior, copy meaning, or functionality — this pass
  changes how the UI looks, not what it does.
- If `{{UI_SCOPE}}` can't be determined and no user-facing screens are
  discoverable, stop and ask instead of guessing.
- A screen is not done until its screenshots pass `DESIGN_RULES.md`.
